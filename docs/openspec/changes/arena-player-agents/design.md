## Context

One independently reviewed change in the arena redesign. See [coordination](../../README.md) and [product specification](../../../product-spec.md).

## Goals / Non-Goals

Deliver bounded player agents and its acceptance scenarios without claiming unrelated work or unverified network support.

## Decisions

- Contract: [capability requirements](specs/arena-player-agents/spec.md).
- Integration boundary: Coordinate player identity and deposit interface with lifecycle and backing.
- Asset identity binds source chain/token, NEAR representation and custody domain.
- Keep custody verifier, oracle, signer, operator and player authorization boundaries explicit. Fixtures do not prove live execution. DAO governance and provider/finality choices remain OPEN.
- Bounded player grants and atomic budget reservations (`contracts/player-policy`, crate `valtrum-player-policy`). Pure policy core plus a persistent NEAR wrapper, isolated from backing/payout/arena. A reservation is an authorization and a budget hold, never a token transfer, proof of funds, custody reservation or confirmed payment; no signing, MPC call or custody access happens here.
  - API (wrapper). `create_grant(input)` — caller is the grant user; creates a grant or a strictly higher version, preserving old versions and the shared budget counters. `revoke_grant(local_id)` — user-only, one-yocto, persistent, idempotent. `reserve(action)` — delegate-or-user only; validates the canonical action against the grant and reserves budget in one transition; idempotent per request identity. Views `get_grant`, `get_budget`, `get_reservation`; events `grant_created`, `grant_revoked`, `budget_reserved` under standard `valtrum_player_policy` v1.
  - Identity and units. `GrantId = sha256(user, local_id)` (version excluded). `request_key = sha256(user, local_id, request_id)` is the idempotency identity (version excluded, so a changed action under the same request is a conflict). `action_hash` binds user, grant version, delegate, exact asset, target, method, destination, amount, gas, request id and battle/community. Token amounts and the authorized/cumulative caps are `U128` atomic units with checked arithmetic; heights/timestamps are `U64`; the gas bound is a declared per-action `U64` unit, explicitly not measured foreign-chain gas. Assets are canonicalized (lowercased 20-byte address) and never identified by ticker.
  - Caller matrix. create_grant: user (caller) only — a delegate/stranger can only create grants where they are the user, never widen another user's. revoke_grant: user only (identity-derived). reserve: delegate or user only — auditor/scheduler/relayer/operator/owner are denied. dispatch / mark_reconciliation: the user or current delegate only (one yocto). confirm_with_receipt: anyone, because the caller has no authority; the registry claim is the evidence. There is no executor role in the normal build. The owner has no path to originate a grant, widen a limit, consume funds or release an obligation.
  - Budget and transition table. Invariant `consumed + reserved <= authorized_limit`; `available = limit - consumed - reserved`. A replacement cannot change the grant's asset identity or lower its cap below consumed plus reserved units; rejected replacements leave the existing version/history/budget untouched. Use a new local grant ID for another asset. Reservation states: `Reserved → Dispatched` (first admission rechecks current version, expiry and revocation), `Reserved → Released` (cancel by user or delegate, or expiry, before dispatch), `Dispatched → Consumed` (confirmed execution, consume exactly once), `Dispatched → ReconciliationRequired` (timeout/missing callback — reservation retained), `ReconciliationRequired → Consumed|Released` (explicit bound evidence). A dispatched obligation can never be released by timeout, restart or revocation alone; conflicting terminal outcomes fail closed. Replacing/revoking/expiring a grant blocks admission of its old queued reservations but does not prevent reconciliation of already-dispatched obligations.
  - External-evidence boundary (#108, D30). Dispatch, reconciliation flagging and consumption run in the normal build; no executor or infrastructure role exists there. `dispatch(user, local_id, request_id)` (user or delegate, one yocto) admits a reservation once, rechecking version, revocation, grant expiry and reservation expiry only at first admission, and requires the reservation to carry a battle id (otherwise no registry receipt could ever bind to it). `mark_reconciliation` (user or delegate, one yocto) flags an ambiguous dispatched obligation and changes no budget. `confirm_with_receipt(user, local_id, request_id, receipt)` is the only consume path: it requires an in-flight (`Dispatched` or `ReconciliationRequired`) obligation, an unused receipt and at least 0.005 NEAR for storage (the rest is refunded), then calls `get_active_claim` on the registry fixed at `new(owner, registry)` (no setter). The private callback `on_receipt_evidence` re-reads state and consumes only if the claim is undisputed and binds exactly: representation, token address, custody domain and mapping version equal the grant's immutable asset; `beneficiary` equals the grant user; `battle_id` equals the reservation's battle; `actual_received` equals the reserved amount; and the claim satisfies the same finality shape the registry and backing check (nonzero hashes and refund address, block not after the finalized head, consistent head hash). The receipt chain id comes from the grant asset, never from the caller. Any failure (null claim from an unknown or disputed receipt, registry error, mismatch, state changed) returns false and refunds the deposit. A consumed receipt is stored in `used_receipts`, so one receipt settles at most one reservation. Events: `obligation_dispatched`, `reconciliation_required`, `obligation_consumed` (with transaction hash, log index and evidence hash).
  - Release of a dispatched obligation. The registry holds deposit-receipt claims only, so no production path proves non-execution and none releases a dispatched or reconciliation-required obligation (not by timeout, revocation, owner or any role). The pure core keeps `NotExecuted` reconciliation and the `sandbox-fixtures` build exposes a single executor-gated `fixture_release_not_executed` for sandbox tests only; a sandbox test asserts neither it nor `set_executor` is callable in the normal build. Whether and how a no-execution proof may release budget is an open decision.
  - Scoped security review. Authentication is the NEAR caller, never a JSON field; infrastructure roles gain no spending authority; grants and budgets persist in contract state so a client restart cannot reset them; a version bump cannot reset obligations or evade the cap; storage growth is charged; NEAR state is public, so no keys, credentials, prompts or unnecessary personal data are stored. Evidence review (#108): the claim is a registry verifier attestation, not cryptographic source-chain proof, so a compromised verifier could consume budget (never spend funds or widen authority); a dispute after consumption does not reverse it; the claim has no request id, so a user's own deposit with the same asset, battle and exact amount can settle the agent's obligation, and one receipt settles only one; a token whose received amount differs from the sent amount never matches and stays held (fail closed); registry unavailability leaves state unchanged and refunds the deposit. Limitation: this enforces budget authorization only — it does not prove custody, real spending enforcement, or that any downstream execution path consumes the authorization; that binding is the deferred executor's obligation.
  - Deferred (open): signed/MPC execution (the policy does not sign or send), a no-execution release path, binding accepted deposits/positions to the user, and MCP/terminal status and revocation integration.

## PR review corrections (2026-11-08)

- Keep chain, token, representation, custody domain and mapping version immutable across versions of one grant ID. The shared budget therefore always measures one asset's atomic units.
- `Budget::relimit` returns an error before mutation if the new limit is below checked `consumed + reserved`; the wrapper validates before writing history or the new version. Exact-use limits remain valid.
- The fixture execution-admission boundary requires the queued reservation's version to equal the current grant version. Regranting after expiry or revocation cannot revive an old queued action; prior dispatched obligations remain resolvable through their original reservation.
- All policy events use NEP-297 `data: [record]`, matching the arena emitter. Canonical grant/action input records reject unknown fields, including nested asset/battle fields, rather than silently discarding uncommitted data.
- Regression coverage includes on-chain replacement rollback, each immutable asset field, cap boundaries, unknown JSON fields, event array shape, expired/revoked version replacement and reconciliation after a grant replacement. These are fixture/policy tests, not evidence of live spending enforcement.
- Grant enforcement (#108, D30). Owner decisions plus agent choices, on `contracts/player-policy`.
  - **Release paths (production build).** `cancel_reservation(user, local_id, request_id)`: the grant's user or current delegate, one yocto, only `Reserved` (also after revocation or expiry), idempotent on `Released`. `release_expired(user, local_id, request_id)`: anyone, one yocto, only a `Reserved` reservation whose expiry has passed; it restores unused budget and cannot spend. Both emit `reservation_released` (reason `cancelled` or `expired`). `Dispatched`, `ReconciliationRequired` and `Consumed` are never changed by either; only explicit evidence reconciles a dispatched obligation. Revocation alone releases nothing.
  - **Expiry.** Each reservation stores `expires_ns = reserve time + TTL`. Default TTL 1 hour (`DEFAULT_RESERVATION_TTL_NS`), owner-configurable within 1 minute to 7 days by `set_reservation_ttl` (one yocto, owner only, affects new reservations only). Expiry is lazy: nothing happens until someone calls `release_expired`, and an expired undispatched reservation cannot be dispatched. A repeated `reserve` for a released request id or an expired, unreleased one fails closed; a new request id is required.
  - **Delegate.** A delegate must differ from the user.
  - **Revocation.** Permanent per grant id: `create_grant` on a revoked id fails, so a version bump cannot re-enable it. The user creates a grant with a new local id, which has its own budget.
  - **Asset.** Immutable per grant id (unchanged), covered by tests for chain, token, representation, custody domain and mapping version.
  - **Limits.** Not decided and not implemented: maximum grant lifetime or past-expiry creation rule, and tying per-grant caps to real deposits. The owner-set TTL can delay budget release for up to 7 days but cannot widen authority.
- Player-agent proposals (#77, D26), in `agent/src/mcp/actions/proposal.ts`, on the #76 action boundary.
  - **Input:** NEAR AI output is untrusted. It must be exactly one JSON object (optionally one ```json fence), `{action: "deposit", user, battleId, community, amount, rationale?}`. Any other field rejects the whole proposal; `rationale` is never an input.
  - **Grant:** comes only from the operator's `PLAYER_AGENT_GRANTS` for the calling delegate.
  - **Conversion:** the proposal becomes a grant deposit request and follows preview, grant pre-check, revalidation and the delegate's `reserve`. Token, recipient (the arena), route, request id and signer come from chain state and configuration.
  - **Status:** `action_status` adds an attribution: user, signer, battle and community, the user's current position, the grant state (revoked, expired, missing), and the on-chain reservation state.
  - **Revocation:** a revoked or expired grant rejects actions that were not prepared; prepared or reserved ones stay attributable.
  - **Not covered:** calling a NEAR AI model and executing a reservation after `reserve` (the reviewed executor adapter) are still open.

## Risks / Migration

Cross-chain operations must be idempotent, reconciled before retry and fail closed on missing evidence. Use isolated testnet deployments; legacy migration is out of scope.
