# Backing implementation and open integrations

The normal contract exposes NEP-141 transfers, storage registration, metadata, accounting views and claiming already-attributed unallocated units. It does not expose receipt observation, finalization, reorganization, reservation, broadcast or redemption confirmation. Because no production verifier exists, no unverified receipt can create unallocated units or supply. As requested, verifier-dependent paths are exercised only by a separate self-call-only sandbox fixture build; never deploy the `sandbox-fixtures` feature.

The internal ledger tracks representation-unit `B = M + E + P + D + U`, with unrepresentable source residue separately attributed to the beneficiary. `get_custody_ledger` converts each bucket to source atomic units and includes residual in `U` and `B`; it returns null when any bucket cannot be represented exactly or arithmetic overflows. `accounting_balanced` reports local arithmetic and supply consistency only, not proof of current Robinhood custody. Receipt identity uses binary transaction hashes and log indexes. Source and representation decimals are fixed at initialization. Redemptions must map exactly back to source units; nonrepresentable dust cannot be reserved.

The standalone receipt-registry contract records immutable operator attestations keyed by source chain, transaction hash and log index. Its owner can authorize representation accounts and rotate the verifier; the verifier funds claim storage. This is not yet integrated with the backing contract, does not independently check finality or custody, and must not be treated as a live mint authorization. A compromised owner or verifier is a trusted testnet risk. Cross-contract callback and recovery behavior remains to be implemented and reviewed.

`evm/src/TestnetDepositCustody.sol` is a deposit-attribution prototype for local fixtures only. It emits token, depositor, a non-zero refund address, beneficiary, battle, mapping version, nominal amount and measured balance increase (event layout changed by D17; deploy under a new mapping version). It has no withdrawal or recovery and must not be deployed or funded. Tests do not establish token eligibility, resistance to dishonest token balance reporting, operator verification, source finality or live custody. Prior direct donations are not included in a later measured deposit; arbitrary malicious token behavior still requires an explicit admissibility policy and independent verification.

Internal reservation state makes redemption and disposal compete for the same representation balance, binds the destination and source amount, and retains a reservation after broadcast or ambiguous response. Internal confirmation checks chain, asset, custody domain, destination, exact debit and recipient amount, transaction and block identities, and consumes each debit identity once per contract. These checks do not authenticate source-chain evidence or prove finality. No DAO authority, source signing, retry/replacement, verified non-execution restoration, or production payout path is supplied here.

A reported reorg pauses the asset and sets reconciliation required without erasing liabilities. There is intentionally no unpause after a dispute until a separately reviewed reconciliation mechanism exists. Storage unregister is disabled, including for zero balances, because an outgoing transfer may still be awaiting a resolver refund; safe pending-transfer tracking and storage cleanup remain necessary. Internal adapter methods currently do not charge for receipt or reservation storage and must not be exposed without storage accounting.

The selected testnet design uses a trusted operator, finalized-head evidence and a shared receipt registry. The verifier account, custody mechanism, actual-received attribution and recovery implementation remain open. Per-contract replay protection alone cannot prevent two contracts from crediting the same custody receipt, and the standalone registry is not yet wired into minting. Before enabling real minting, authenticate the operator and registry, integrate cross-instance replay protection, verify actual custody balances and reject unproven finality. Real Robinhood execution and lifecycle integration are not established by fixtures. See the task list for completed, individually verified work and remaining integration gates.

The agent-side operator verifier (`agent/src/custody-verifier.ts`, with `custody-event.ts`) checks one custody deposit event against a committed asset mapping. It requires the RPC `finalized` head, walks parent hashes from that head to the receipt block, matches log and receipt block/transaction hashes, rejects failed, wrong-token, wrong-version, wrong-battle, unattributed and already-consumed receipts, and requires token `Transfer` logs into custody to equal the measured deposits and the custody balance to grow by at least that amount across the block. Unavailable, unfinalized or non-canonical evidence stays Pending. It is tested only against injected fixtures: it is not wired to the registry or to a live RPC adapter, the operator account is not authenticated here, and the `isConsumed` hook must be backed by the shared registry before use. Malicious or rebasing token behavior remains an admissibility gate.

`claim_receipt(transaction_hash, log_index)` is the pull-based mint entry. The registry account and mapping version are immutable constructor arguments. The call asks the configured registry for `get_active_claim`, and the callback credits the claim's beneficiary into attributed unallocated custody only if the claim matches the asset (token, custody domain, mapping version, this representation account, consistent finalized evidence). Absent, disputed, mismatched, replayed or paused outcomes credit nothing and refund the full deposit; a replay also finds the receipt already finalized. Storage is paid from a 0.02 NEAR deposit, with the unused part refunded. Conversion into NEP-141 supply still requires the beneficiary's explicit `claim_representation`. `report_registry_dispute(transaction_hash, log_index)` lets anyone pull a registry dispute: if the registry confirms it for a receipt this contract credited, the asset pauses and reconciliation is required with liabilities retained; unknown receipts, unavailable registry answers and undisputed receipts change nothing, and there is no unpause path yet. Not yet done: live deployment or operator wiring. Sandbox tests use synthetic attestations, not live finality.

`allocate_entitlement(allocation_id, beneficiary, amount)` is the settlement hand-off. Only the arena account fixed at initialization may call it. It burns that amount of the arena's locked representation, moves the same backing from minted to entitlements, records an immutable allocation (idempotent by id; conflicting data fails), and charges storage from the attached deposit. It does not itself prove that the amount belongs to a losing vault or a final result; settlement must call it only for allocations it has computed. Entitlement payout reservation, DAO disposal from entitlements and the arena-settlement ABI remain unimplemented.

`reserve_entitlement` (Rust-only, not an ABI method) reserves part of a beneficiary's settlement entitlement for one original-token payout, moving it from entitlements to payouts before any signature is requested, bound to destination and request identity and idempotent per request. Redemption, payout and disposal reservations draw from disjoint pools (token balance versus entitlement) and the same bucket arithmetic, and `confirm_redemption` consumes a broadcast payout once with exact evidence. The Rust-level reservation primitives do not authenticate the beneficiary, delegate or DAO. Payout reservations are now reached through `reserve_payout`, `confirm_payout` and `release_payout`, callable only by the payout account fixed at initialization (see the `arena-chain-signatures` notes): the payout contract authenticates the holder, confirms only matching attested evidence, and releases a reservation only before any signing request or after an attested nonce-slot proof; timeouts and missing responses never release. Redemption and DAO disposal reservations have Rust-only `confirm_redemption`, `confirm_disposal` and `release_unspent_reservation` (no entry point until DAO authority is designed). Payout reconciliation is complete: `report_unresolved_reconciliation` (payout account, one yocto) suspends the asset until `confirm_payout` or `release_payout`.

Suspension and resume: see the design. Entry points: `set_operator`, `attest_custody_balance`, `resume`, `set_resume_policy`, view `get_suspension`. Events use `standard: valtrum_backing`, `version: 1.0.0`: `operator_changed`, `resume_policy_changed`, `custody_attested`, `asset_suspended`, `asset_resumed`, `reconciliation_unresolved`, `late_deposit_recorded`.

Late deposit refund interface for the payout contract (not implemented there; issue #62): the `destination` must equal the refund address bound at deposit (it appears in `get_late_deposit` and `late_balance_of_refund(account, refund_address)`); any other value fails with `UnboundRefundAddress`. Call `reserve_late_refund(beneficiary, request_id, amount, destination)` with one yocto from the payout account; it returns `{created, source_amount}`. The deposit event names a NEAR account, so the payout contract must authenticate that beneficiary when choosing the source-chain destination. Then call `confirm_payout(beneficiary, request_id, evidence)` after a finalized transfer or `release_payout` after a no-spend proof. Views: `late_balance_of`, `get_late_deposit`, `payout_reservation_status`. The task for the actual return stays open until payout executes it.

Refund address (D17): `RegistryClaim`/`Claim` gained `refund_address: [u8; 20]` (JSON array like `destination`); the registry and `matches_asset` reject all-zero. `LateDeposit` gained `refund_address`, the `late_receipts` receipt carries it, and the `late_deposit_recorded` event adds `refund_address`. Fixture receipts use `0xbe` repeated, which is a fixture value and not live evidence. The agent verifier output `FinalizedAttestation.refundAddress` and includes it in the evidence digest. The payout contract's choice of destination (issue #62) is not changed here and must pass the bound address.
