# Backing implementation and open integrations

The normal contract exposes NEP-141 transfers, storage registration, metadata, accounting views and claiming already-attributed unallocated units. It does not expose receipt observation, finalization, reorganization, reservation, broadcast or redemption confirmation. Because no production verifier exists, no unverified receipt can create unallocated units or supply. As requested, verifier-dependent paths are exercised only by a separate self-call-only sandbox fixture build; never deploy the `sandbox-fixtures` feature.

The internal ledger tracks representation-unit `B = M + E + P + D + U`, with unrepresentable source residue separately attributed to the beneficiary. `get_custody_ledger` converts each bucket to source atomic units and includes residual in `U` and `B`; it returns null when any bucket cannot be represented exactly or arithmetic overflows. `accounting_balanced` reports local arithmetic and supply consistency only, not proof of current Robinhood custody. Receipt identity uses binary transaction hashes and log indexes. Source and representation decimals are fixed at initialization. Redemptions must map exactly back to source units; nonrepresentable dust cannot be reserved.

The standalone receipt-registry contract records immutable operator attestations keyed by source chain, transaction hash and log index. Its owner can authorize representation accounts and rotate the verifier; the verifier funds claim storage. This is not yet integrated with the backing contract, does not independently check finality or custody, and must not be treated as a live mint authorization. A compromised owner or verifier is a trusted testnet risk. Cross-contract callback and recovery behavior remains to be implemented and reviewed.

`evm/src/TestnetDepositCustody.sol` is a deposit-attribution prototype for local fixtures only. It emits token, depositor, beneficiary, battle, mapping version, nominal amount and measured balance increase. It has no withdrawal or recovery and must not be deployed or funded. Tests do not establish token eligibility, resistance to dishonest token balance reporting, operator verification, source finality or live custody. Prior direct donations are not included in a later measured deposit; arbitrary malicious token behavior still requires an explicit admissibility policy and independent verification.

Internal reservation state makes redemption and disposal compete for the same representation balance, binds the destination and source amount, and retains a reservation after broadcast or ambiguous response. Internal confirmation checks chain, asset, custody domain, destination, exact debit and recipient amount, transaction and block identities, and consumes each debit identity once per contract. These checks do not authenticate source-chain evidence or prove finality. No DAO authority, source signing, retry/replacement, verified non-execution restoration, or production payout path is supplied here.

A reported reorg pauses the asset and sets reconciliation required without erasing liabilities. There is intentionally no unpause after a dispute until a separately reviewed reconciliation mechanism exists. Storage unregister is disabled, including for zero balances, because an outgoing transfer may still be awaiting a resolver refund; safe pending-transfer tracking and storage cleanup remain necessary. Internal adapter methods currently do not charge for receipt or reservation storage and must not be exposed without storage accounting.

The selected testnet design uses a trusted operator, finalized-head evidence and a shared receipt registry. The verifier account, custody mechanism, actual-received attribution and recovery implementation remain open. Per-contract replay protection alone cannot prevent two contracts from crediting the same custody receipt, and the standalone registry is not yet wired into minting. Before enabling real minting, authenticate the operator and registry, integrate cross-instance replay protection, verify actual custody balances and reject unproven finality. Real Robinhood execution and lifecycle integration are not established by fixtures. See the task list for completed, individually verified work and remaining integration gates.
